# 0.7.4 聊天来源、事件状态与启停恢复审查

日期：2026-11-12。基线：0.7.3。本轮对应：

| 审查项 | 验收目标 |
| --- | --- |
| 第二：聊天来源、工具调用、邀请与回应状态 | 普通聊天与插件事件分开，提交成功不冒充实际完成 |
| 第三：启停、重载、升级、失败重试 | 中断不污染新会话，已保存进度可恢复，受支持的旧存档继续可用 |

只修改插件代码和文档。不修改宿主，不安装或重载实际插件，不操作真实存档，不向真实角色发消息、送礼或邀请，也不请求真实模型。

## 宿主接口证据

只读核对相邻宿主源码：

- `main_logic/core/turn.py`：普通用户与角色回复发布为 `user_message` / `assistant_message`；`metadata.ts` 为消息发生时间，转发后的顶层 `timestamp` 为总线到达时间。
- `main_logic/agent_event_bus.py`：普通聊天的 `conversation_id` 仅作诊断上下文，不承诺一问一答的配对。
- `main_logic/omni_offline_client/_lifecycle.py`：离线主动事件在请求实际开始后发布 `proactive_instruction`，回复提交后发布 `proactive_reply`，二者共享同一 `conversation_id`。
- `app/agent_server/api_runtime.py`：转发消息保留角色、类型、关联 ID 与时间；主动通道不保证保留插件自定义的完整事件元数据。
- `plugin/sdk/plugin/base.py`：`push_message()` 回执只表示立即提交到本地，不证明宿主消费、生成回复或播放完成；工具注册也包含本地登记和异步通知。

因此普通聊天继续按角色与消息发生顺序配对；插件主动事件通过自身请求标记及主动指令/回复的关联证据识别，不套用普通聊天的诊断 ID。

## 已修复的问题

新增定向回归先验证问题，再修改实现。旧存档兼容等原本正常的流程补充保护性测试，不把通过的用例计为新缺陷。

| 问题 | 原行为与影响 | 修复 |
| --- | --- | --- |
| 总线与历史的特殊来源过滤不一致 | 带明确关系提示、工具、代理或特殊来源标记的总线记录仍可能进入普通聊天判断 | 两条路径复用同一特殊消息判定；总线同时检查外层来源与嵌套元数据。不依赖未知来源白名单 |
| 两种来源的并发竞态 | 历史请求开始后，总线已选定该角色来源；迟到历史结果仍被处理，导致同一轮被观察两次 | 历史结果应用前在锁内再次核验来源，已选总线的角色跳过历史结果 |
| 迟到的旧用户消息被算成新聊天 | 插件启动前的消息在启动后才转发，单靠到达游标无法排除 | 总线游标保留本次启动起点，普通用户消息还须满足发生时间不早于该起点 |
| 去重只比较前 40 字 | 同时间、同角色、相同前缀的不同消息被合并 | 对原始全文计算独立指纹，避免截断和金币文本归一化抹去标点差异 |
| 异常总线返回被当作可读 | `None`、字典错误对象或字符串被转成空结果，误报总线读取成功 | 拒绝不符合列表型协议的返回并记录 `invalid_result`，兼容历史仍可继续读取 |
| 送礼不明确回执被当作拒收 | `None`、缺失字段、整数或字符串形式的提交值被标为不可用，30 秒后可重试 | 只有布尔 `submitted=false` 表示明确拒收；其他不确定值保持 `unknown`，等待至少 120 秒 |
| 邀请核对丢失状态 | 原邀请成功提交，但沿用原请求核对只返回旧事务结果，界面退回未知 | 重放事务后附上当前草稿的邀请状态，不重发邀请；重启后状态恢复为未知时也如实返回未知 |
| 无关主动消息冒充告白送达 | 仅角色一致、文本像告白就标记本插件告白已送达，后续一句同意可能确认关系 | 每次请求保存独立 `request_id`，要求事件身份与完整关联键匹配，或先观察含请求标记的主动指令，再关联同一主动回复；仍保留角色、时间、内容及截断校验 |
| 旧告白回复关联新尝试 | 旧请求迟到后，没有独立请求身份可用来区分 | 当前尝试身份必须一致，旧标记不确认新请求；身份随存档保存，重载不重发 |
| 不确定告白重复释放次数 | 收不到可核实回复或发送中断时退还次数，多轮重启后请求数突破 3 次 | 已持久占用的次数保留；修复前的多轮重启场景实际发出 6 次，修复后最多 3 次。失败或缺失证据不能证明请求从未送达 |
| 启动期间停用后重新激活 | 读盘或素材初始化的异步结果返回后，旧启动仍设置就绪、启动线程、注册工具 | 启动准入标记拒绝重叠启动；文件准备与素材共用独立锁，由停止流程排空，激活前再次核验启停代次 |
| 初次保存失败异常外抛 | 没有完整启动错误结果，无法稳定区分失败与就绪 | 返回启动失败，保持未就绪；存储恢复后可以再次启动 |
| 重载保留旧工具和缓存 | 状态查询工具描述不变，可能被旧注册记录跳过；旧角色集合和提示重试时间继续生效 | 成功启动时注销旧绑定并重新注册，更新工具会话，重置宿主探测、角色可用性、提示、消息时间、素材和来源缓存 |
| 旧查询工具跨会话修改活跃日期 | 旧工具闭包在新会话就绪后仍能写新记录 | 查询工具绑定创建时的启停代次；旧会话调用返回错误 |
| 迟到邀请跨会话或跨尝试提交 | 保存邀请与实际排队之间发生重载或后续邀请，旧工作仍可能发送 | 发出前核对启停代次、草稿 ID、请求时间和请求中状态；重载或新尝试使旧发送失效 |

无关主动回复不能确认本插件告白，但在已核实告白后插入其他话题仍会提高对后续答应语句的要求，防止一句泛泛的“我愿意”答错问题。

## 状态语义

| 状态或操作 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 送礼结算成功 | 礼物消耗、实际好感与交易回执已经一起保存 | 角色已回复 |
| 送礼回应 `submitted` | 本地提交明确成功 | 宿主已消费、角色已生成或已播放 |
| 送礼回应 `received` | 观察到可关联到对应礼物与角色的主动回复记录 | 语音或动画已播放 |
| 邀请 `submitted` | 本地提交明确成功 | 模型已参与共创、草稿已更新或内容已留存 |
| 模型工具草稿更新成功 | 待确认草稿已保存 | 玩家已经确认正式便签或现实事项结果 |
| 面板“确认留存”成功 | 已确认的记录保存成功 | 已进入角色当前上下文 |
| 关心提示已安排 | 已保存一次性发送安排 | 模型已读取或实际问了问题 |
| 告白请求处于等待 | 一次请求已尝试，等待核实回复与玩家同意 | 已送达或双方已确认恋爱 |

未知提交不冒充明确拒绝；提交成功不冒充生成或播放完成。提示是否被模型遵循仍属于实机验证范围。

## 恢复与兼容

- 关系存档格式继续为版本 3，经济格式继续为版本 2，共同经历格式继续为版本 1。主动告白新增可缺省的请求身份字段；旧存档缺失时规范化为空，不清除关系、好感、余额、库存或历史。
- 对关系格式 1、2、3 的样本逐次启动两次，验证已确认恋爱、好感、独立角色、余额和库存保留。原有旧经济迁移备份、旧交易重放、称呼备份与迁移继续由全量回归覆盖。
- 已保存的草稿与正式内容重启保留。未核实的邀请和送礼回应不自动重发；核对原交易不再次扣币、消耗礼物或增加好感。
- 保存失败的原子性、同请求重试、确认后刷新失败、停止中评分取消、停止超时禁止重启和迟到查询结果隔离继续保留。
- 启动失败保持未就绪；恢复存储后可以重新启动。损坏或不支持的存档继续保留并拒绝启动，不用新钱包覆盖。
- 停止会排空已经接纳的启动或素材文件操作。普通消息、工具和邀请在代次检查后才应用；旧异步读取不能污染新会话。

结果不确定的主动告白也占用尝试次数，这是本轮对边界的明确收紧：宁可少发一次，也不因为缺失回执反复发送。正常聊天中由角色工具确认双方关系的路径仍可使用。

## 验证边界

- 宿主不提供跨插件保存与消息消费的同一事务，无法保证消息既绝不遗漏又绝不重复。预先保存安排后中断，可能少发一次；不明确结果由用户核对或按冷却重试。
- 缺少主动事件关联证据时，保持未核实，不用无关回复兜底。升级前没有请求标记的未送达告白不会凭猜测确认；已记录的关系事实保留。
- 尚未成功落盘的评分和金币进度重试只在内存中；进程中断后不保证补算。已返回结算成功的数据已完成原子保存，保持可恢复。
- 短时间超过宿主总线最近记录窗口，或宿主历史完全替换，可能漏观察消息。兼容读取会重建基线，避免把旧记录重新计分；本轮没有新增宿主不支持的可靠消费协议。
- 模型是否正确调用工具、导入后的正常聊天、主动告白与送礼回应，以及语音播放，都需要导入新版后的实机验收。
