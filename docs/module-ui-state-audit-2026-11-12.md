# 0.7.5 模块职责、重复逻辑与界面状态审查

日期：2026-11-12。基线：0.7.4。本轮对应第四项“模块职责、重复逻辑、界面状态”，目标是后续新增玩法更容易定位和验证。

只修改插件源码、测试和文档；不修改宿主、不安装或重载运行插件、不操作真实存档、不向实际角色发送消息、不调用真实模型。

## 已复现的问题

在修改运行代码前新增五个浏览器回归，五项均失败。修复后五项通过，并纳入全量回归。

| 场景 | 原行为 | 修复 |
| --- | --- | --- |
| 共同经历返回空结果 | 仍显示保存成功，清除原请求并关闭表单 | 解包失败保留请求与输入，提示核对原操作 |
| 创建便签收到另一操作的回执 | 只要有 `operation` 就视为成功 | 核对操作、修订以及已有对象 ID；不匹配保持未知 |
| 购买只返回数量，缺少商品和余额 | 仍生成购买成功文案，清除请求 | 校验本动作所需字段及商品身份；回执不完整不确认 |
| 通信错误包含 `shop_stale_extra` | 按子串识别成 `shop_stale`，清除原请求 | 按完整错误标识匹配，不截取较长错误码 |
| 错误通过结构化 `code` 返回 | 只读消息字符串，没有识别明确拒绝 | 优先识别结构化错误码；冲突要求刷新并重新核对 |

商店回执还会核对赠送角色、预期加分和领取期间；共同经历回执核对操作对应修订及已有内容身份。只验证当前消费的协议字段，不把前端校验当成后端安全边界。

## 职责与重复逻辑

- 新增 `_commerce.py`，集中领取、购买、送礼及回执重放的跨域规则；不引入 SDK、网络或文件接口。时间和日期由调用者传入，关系增量和活跃日使用同一次结算时间。原入口在同一状态锁与整体事务内调用，仍先保存再使评分失效或通知阶段变化。
- 返回 `Settlement(result, replayed)`，让入口显式区分首次结算和回执核对。旧交易签名、角色范围、库存、每日额度、告白门槛及原子回滚保留；未知内部动作名明确拒绝，不再落入默认送礼分支。
- 新增 `ui/requests.ts`，统一共用 `RunAction` 类型、错误码与冲突判定、有限层返回值解包，以及提交确认和刷新结果。玩法组件负责校验自己的回执字段，通用模块不生成请求 ID、不修改玩法状态。
- 面板、商店、共同经历和立绘导入复用同一解包逻辑，删除四份不同的遍历实现。无目标字段的返回抛出未核实错误，不再默默变成空对象或保存成功。
- 新增 `ui/refresh.ts`，合并两份定时刷新生命周期；读取完成后才安排下一次，隐藏、操作或编辑弹窗打开时暂停，离页后不再安排新轮询。它只读取显示，不发送邀请、结算或自动重试保存。
- 新增 `docs/module-map.md`，列明后端与界面状态的所有者、对应测试、请求状态语义和新增玩法步骤；`DESIGN.md` 指向当前职责说明，保留旧章节作为沿革。

入口类和面板仍承担多项编排职责。本轮只拆出边界清楚、能够独立验证的部分，没有大规模搬动生命周期、评分线程、锁或模型工具绑定。没有新增运行依赖，没有改存档格式或迁移策略。
