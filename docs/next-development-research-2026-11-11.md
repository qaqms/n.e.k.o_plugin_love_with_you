# 后续开发调研：共同经历、角色差异与长期相处

调研日期：2026-11-11。当前插件版本：0.6.4。

本文保留基于 0.6.4 的产品研究与开发建议。2026-11-11 实施更新：0.7.0 已实现「一起写便签」和「以后关心」两个原型，新增「共同经历」页、按参与角色保存、玩家确认留存与被动聊天回顾；具体范围、限制和操作见 README 与使用指南。下文其他建议仍是后续方向，调研时的测试数量仅代表当时基线。宿主 `D:\neko kaifa\N.E.K.O` 仅供只读接口核对，开发仍限制在本插件。

2026-11-12 范围更新：用户决定宿主未提供的接口能力暂不开发。主桌宠身体分区识别、分部位触摸回应、直接动作与表情控制、自定义头顶气泡均不列入当前开发范围，不新增宿主桥接。后续继续以现有聊天接口和插件面板完善共同经历、关系阶段差异及回访内容。

## 1. 建议结论

下一轮优先验证桌宠“如何与玩家发生共同经历”：从聊天中明确的约定、真实的插件操作和用户发起的陪伴开始，保存可核对的结果，在后续对话中自然回访。

根据用户提出的桌面形态问题，实施顺序调整为先验证交互载体，再决定剧情数量。下文的约 8 个片段是载体验证通过后的候选内容，不是下一步直接开工的任务清单。

推荐顺序：

1. 聊天中的约定、可管理的共同回忆、后续回访组成最小完整体验。
2. 在同一轮里提供恋人阶段内容，让已经确认关系的玩家也有新体验。
3. 扩充角色偏好、送礼差异、共同计划及轻量陪伴。
4. 内容框架稳定后，再开放事件包与装饰收藏。

理由是现有插件已经实现数值成长、确认关系、称呼、日期、奖励与赠送，但新增关系深度还需要回答三个问题：一起经历了什么、这次选择留下了什么、成为恋人之后还能共同做什么。桌宠还需要先回答：这些经历通过哪个界面和哪种交互真正发生。

以上是结合代码和样本机制做出的产品判断，不是经用户实验验证的效果结论。游戏的成功也不能证明某一机制单独造成了成功。

## 1A. 桌宠如何与玩家发生事件

### 交互载体优先

建议把事件定义为“有起因、玩家参与、可确认结果和后续影响的一段相处”。一次普通聊天也可以构成事件，但只随机说一句甜话还不够。

| 事件载体 | 玩家如何参与 | 可以留下的结果 | 当前判断 |
| --- | --- | --- | --- |
| 聊天中的约定与回访 | 自然语言提出、接受、修改或取消 | 用户认可的约定、后来反馈的结果 | 最适合先验证；依赖模型正确调用工具 |
| 插件面板中的共同选择 | 角色提出建议，玩家预览并确认 | 实际保存的主题色、选定的纪念日等 | 有可核对结果，可复用已有操作；联动尚未实现 |
| 用户发起的短时陪伴 | 明确开始、暂停、结束并反馈 | 相处时段及用户报告的体验 | 可以做，但倒计时本身未必有价值 |
| 自愿进入的虚构情境 | 明确选择文字茶歇、故事或角色扮演 | 虚构情境内的选择与结局 | 可作为扩展，不能默认当成现实经历 |
| 桌面触碰、表情、动作与气泡 | 点击桌宠或通过宿主原生交互参与 | 视觉或语音反馈 | 已核实本机宿主：有原生点击反馈与演出，但未发现当前插件可用的触摸事件订阅或直接演出控制接口；聊天可间接触发既有情绪反馈 |

聊天承担自然表达，面板承担需要精确确认的操作、当前状态和回忆管理。不要要求每次互动都打开面板走固定选项，也不要仅凭模型一句“完成了”就写入事件结果。

2026-11-11 接口核实详见 [桌宠交互接口核实](desktop-interaction-interface-audit-2026-11-11.md)。聊天文字展示与桌宠头顶情绪气泡是不同通道；主页面的 JavaScript 控制方法不等于 Python 插件 SDK 能力。

### 建议的首个原型：记得一件正在发生的事

这是候选体验，不是当前已经具备的能力。

1. 玩家说“明天下午有个面试，有点紧张”。
2. 角色先正常回应，按人设询问是否希望下次聊到时问问结果。
3. 玩家同意后，保存一条简短待回访事项；不保存整段谈话。日期按玩家明确表达和本地日期解析，不擅自补时间。
4. 约定日期之后，下一次玩家主动开聊时，角色得到一次低优先级回访提示；不在玩家没出现时连续发消息。
5. 玩家可以报告结果，也可以说暂时不想谈。报告结果由用户确认后保存，拒绝则暂停或关闭回访，不扣好感。
6. 后续适当时刻可以提及这段经历，但不推断玩家最终被录用、失败或实际参加了面试。

它与一次性提醒的区别在于保留“双方约定、用户反馈和后续回应”；与通用聊天记忆的区别在于范围明确且可由用户管理。是否因此增加陪伴感，仍需要试玩验证。

### 第二个原型：一起决定一个能看见的结果

例如一起给插件面板选择配色。角色提出两种表达风格，面板展示真实预览，由玩家最终确认保存。后续可以记得这次共同决定。

此例复用现有主题能力，但目前尚未实现聊天与配色选择的联动。颜色设置是全局的，不能把一位角色参与选择误写成其他角色都参与过。插件立绘是装饰图库，选择立绘也不能描述成已经替换宿主角色模型或给桌宠换装。

### 可并行评估的玩法原型：一起完成一份小作品

仅有待办回访可能更像记事功能，因此还需验证“玩家参与过程是否有趣”。一个轻量候选是与角色一起写一张给以后回看的便签。

开场由用户选择或接受；双方轮流补一句，也可以选主题、改写或结束。最终文字由玩家确认后才保存。在明确的未来节点或用户主动打开时，再让角色依据真实成品回顾。

它能够形成开场、参与、结果与后续，又不要求额外的世界地图、桌面动作或外部应用控制。作品本身是新增持久内容，需要单独的保存、删除与隐私说明，不能静默套用现有评分记录。

如果玩家只想聊天，活动可以完全通过自然语言推进；面板仅用于查看状态、确认保存和管理作品。是否自动邀请、多久邀请，等主动发起的版本验证后再决定。

### 模板与自由对话的分工

模板只限定发生条件、允许做什么、当前进展与可保存的结果。角色自己的措辞由宿主聊天模型按原有人设生成，不给所有角色套相同台词。

自然语言决定存在不确定性时，应澄清或保留待确认状态；精确保存可以由面板兜底。需要玩家回答的问题只有一个时，不强制展开成多项分支剧情。

### 原型通过的最低标准

- 玩家能理解角色为何在这时提起这件事。
- 参与、拒绝和中断都能自然完成。
- 结果可核对，切角色和重启后不会错误归属。
- 下一次回访能承接真实结果，且不会重复追问。
- 不依赖额外金币奖励，仍有人愿意使用。
- 宿主的通用记忆若已能稳定完成同一体验，插件应缩小范围，避免重复建设。

## 2. 研究方法与样本

材料主要采用官方玩法介绍、开发者公告、项目文档、公开源码与 GDC 开发者演讲；未把商业宣传中的留存效果当成实验事实。

样本分为商业游戏、经典养成作品和邻近技术项目，并非“当前热度排行榜”。乙女游戏和其他玩家群体的偏好不能直接等同于本插件用户偏好；借鉴机制，需要在本插件中验证表达与舒适度。

热度与代表性的可核对依据：

- 《恋与深空》美区 App Store 页面在本次读取时显示约 6.2 万条评分，作为覆盖规模的一个有限信号；评分量不代表活跃用户，不能据此推导某项玩法有效。[S1]
- 《星露谷物语》官方 press 页面披露截至 2024 年 12 月累计销量超过 4100 万；这是历史节点，不能写成 2026 年最新销量。[S2]
- 2026-11-11 读取的 GitHub 页面显示，AIRI 约 51.3k stars，SillyTavern 约 35.5k，MAS 约 1.4k。星标只说明公开关注度，不等于活跃用户或体验质量；MAS 入选主要因为长期角色陪伴的贴合度。[S11][S14][S15]
- 《心跳回忆 GS4》作为经典系列的机制样本，不据此声称它在当前市场热度最高。

## 3. 从样本提炼的设计原则

### 3.1 关系发展要产生可感知的新互动

建议用具体相处片段表达阶段变化。例如陌生时礼貌地一起选茶，熟悉时能回访上次选的口味，恋人时一起准备一个小纪念日。区别应落实在活动、选择和回访中。

这也符合 GDC 2025《Designing Relationships》的开发者框架：同伴参与事件、表达观点、回应玩家选择，并通过相处建立信任。该演讲是设计经验，不是量化实验。[S16]

### 3.2 保存结果，比堆积对话更适合当前插件

“因为认真关心而 +2”适合评分记录；“我们约定下次一起选一部轻松的电影”适合作为共同经历。两者用途不同。

建议仅保存少量用户认可的事实摘要、事件选择、时间与后续线索。自动摘要应先作为候选，允许核对、修改和删除。SillyTavern 官方同样明确说明模型摘要可能遗漏与幻觉。[S13]

### 3.3 有差异的选择，不必都有输赢

选红茶或咖啡、聊今天或安静坐一会，可以改变本次片段和之后的回忆。它们不必分别对应“正确答案 +3”和“错误答案 -3”。

插件可以保留好感规则，同时通过偏好和内容分支表达差异，减少猜标准答案的倾向。这是建议，需要实机试用验证。

### 3.4 恋人是内容的开始之一

建议第一轮新内容就包含恋人阶段。共同计划、两人的小习惯和纪念片段可以继续发展，避免把新增内容全部放在告白之前。

不预设恋爱必须升级为同居、结婚或育儿；如以后提供这些分支，作为用户明确选择的独立内容。

## 5. 功能优先级

这里的收益和成本为定性估计，并非工期承诺。

| 优先级 | 功能 | 预期体验变化 | 主要成本与依赖 |
| --- | --- | --- | --- |
| 首先验证 | 聊天约定 + 共同回忆 + 回访 | 玩家说过的事能够被准确承接 | 明确意愿、事件状态、角色归属、模型执行可靠性 |
| 原型通过后 | 短事件与共同选择 | 今天的选择能在以后被记得 | 内容编写、实际操作联动、可确认结果 |
| 第一轮一起做 | 恋人日常片段 | 确认关系后仍有新内容 | 与关系事实一致的文案和分支 |
| 第二轮 | 角色活动与表达偏好 | 不同角色相处方式有所不同 | 与宿主人设的优先级、来源和冲突处理 |
| 第二轮 | 轻量陪伴与共同计划 | 有聊天之外、可反复开展的活动 | 中断恢复、时间状态、邀请频率 |
| 第二轮 | 礼物故事与纪念事件 | 已有商店和日期功能产生更多内容 | 礼物与事件关联，避免重复奖励 |
| 后续 | 内容包与经历纪念物 | 更容易持续扩展内容 | 格式版本、校验、本地化、导入管理 |
| 延后验证 | 短期相处状态 | 区分近期气氛与长期关系 | 误判、解释、恢复机制，容易增加维护负担 |

### 5.1 第一轮：共同经历

建议先完成 1A 的原型，再决定是否扩展成以下小版本；不拆成“先做好看的回忆列表，以后再让角色记得”。

最小范围：

- 3 个可主动选择的活动模板：茶歇、文字情境散步、一起决定一件小事。
- 总计约 8 个短片段，覆盖初识、熟悉、好感、暧昧与恋人；其中至少 2 个为确认恋爱后的片段。数量是内容控制目标，可在试玩后调整。
- 每个片段有开场、1 至 2 个有实际区别的选择、结束条件和一条回访线索。
- 用户能够拒绝、暂停或结束；未完成不扣分。
- 结束后生成待确认的简短留念，用户决定是否保存。
- 回忆页能查看、编辑、删除，以及停止后续引用。
- 后续适合的话题或再次开展活动时，按预算带入少量相关回忆。

示例流程仅说明新设计，不是现有能力：

1. 用户选择与当前角色进行一次文字茶歇。
2. 角色按原有人设开启片段，询问想热闹聊天还是安静坐一会。
3. 用户选择安静陪伴，事件记录本次选择，不立即认定这是永久偏好。
4. 用户结束后，界面询问是否保留“今天一起安静喝了一杯茶”。
5. 下次相关活动中，角色可以问“这次也想安静坐一会吗”，不能直接断言用户一直如此。

文字情境活动需要与现实活动明确区分。定时器到点不证明用户真的学习、散步或完成任务；角色也不能编造观察到了现实行动。

### 5.2 第二轮：角色偏好与差异

建议先使用少量可编辑的描述，不增加一整套性格参数。

可包含：

- 角色认可或用户设置的活动偏好。
- 用户喜欢的互动方式，例如安静陪伴、轻松玩笑、直接表达。
- 明确的互动边界，例如不希望主动邀请或不喜欢某类剧情。
- 已经共同完成的小计划，或明确约定以后尝试的活动。

宿主人设继续决定角色是谁；插件偏好补充相处方式，不擅自改写角色身世。一次活动选择不自动变成永久偏好。

礼物可先改变回应内容和回访，不急于改变价格与好感收益。例如角色知道某次花束是为庆祝一件具体事情送的，之后能在纪念时提起。

### 5.3 第二轮：陪伴与共同计划

可做用户发起的 10 分钟茶歇、25 分钟专注或一周内一起完成的小计划。时长仅为候选，不作为玩法结论。

陪伴允许暂停、退出和安静运行；完成不额外发币，先观察它本身是否有使用价值。共同计划主要保存双方明确约定与用户报告的结果，不监视实际行为。

主动邀请应独立开关、低频、可延后。拒绝或未回复不作为感情拒绝，不扣好感。

### 5.4 后续：事件内容包

事件框架跑稳后，再提供可验证的数据格式。建议内容字段包含标识、适用阶段、必要关系事实、角色限制、触发条件、冷却、分支、结束条件与回忆模板。

内容包仅包含数据，不运行第三方脚本。先用内置内容验证格式和本地化，再考虑用户导入。

## 6. 暂不优先的内容

- 再增加多条“信任、依赖、占有、心情”数值：先验证现有好感加事件是否足够表达差异。
- 把结婚设成强制下一阶段：它无法替代日常内容，且需要新的明确关系确认。
- 更重的签到、连续在线或离开惩罚：现有经济已有互动进度，新增内容不必继续提高维护要求。
- 只扩充礼物商品与立绘数量：可以增加选择，但还不能验证共同经历和后续回应。
- 大型战斗、种田、家园装修、3D 约会：内容和技术成本明显扩大，容易脱离当前插件边界。
- 全自动记录所有聊天为长期回忆：与现行“不保存聊天原文”的承诺不同，也容易积累错误事实。

这些是对当前资源和产品定位的取舍，不表示相应玩法在其他作品里没有价值。

## 7. 不改宿主的实现范围与约束

以下是基于现有接口的可行性判断，需通过原型验证；不承诺聊天模型必然执行提示。

### 7.1 可以复用的入口

- Hosted TSX 面板：活动选择、分支确认、回忆管理。
- 动态 LLM 工具：读取活动状态、提交经过校验的选择或结束请求。
- `push_message(ai_behavior="read")`：提交当前活动与相关回忆的简短上下文。
- 现有 `respond` 路径：在用户发起或已许可的邀请中请求角色回应。
- 插件数据目录与 `StateFile`：保存结构化事件和回忆。

宿主 SDK 明确说明发送回执只代表本地提交，不代表模型已消费、已生成或已播放。新事件同样必须区分“请求已提交”和“事件已完成”，不能看到提交成功就自动记作真实共同经历。

### 7.2 状态、并发与重新开始

- 事件绑定参与角色、关系范围、唯一标识及预期修订号；旧面板、切换模式或重新开始后，过期结果不得完成新关系的事件。
- 保存成功后才能发布完成结果；重复请求复用同一回执，沿用现有事务与失败回滚思路。
- 中断、保存失败和发送结果未知都需要独立状态；重启不自动重复请求不确定的演出。
- “重新开始关系”取消进行中的事件；历史回忆可以保留为过去经历，但不能继续当作当前恋爱承诺。具体保留入口在实施设计时明确。
- 共用好感下建议数值继续共用，但新经历仍记录实际参与角色。其他角色只有经显式共享才可引用；这是待实施的产品建议。

### 7.3 评分与经济

内部提示、自动剧情文本与系统回执不进入普通聊天收入，也不重复评分。

真实用户参与的普通聊天仍按已有规则计算一次。第一轮不为事件完成额外发币或加分，避免先引入新的奖励漏洞与平衡问题。

### 7.4 记忆与用户控制

新回忆功能会新增内容持久化，必须更新使用指南并让用户主动启用；当前版本仅有的数值和理由不能被误称为已经存在完整共同回忆。

建议保存类型、参与者、事件来源、时间、简短摘要、用户确认状态与引用开关，避免保存整段聊天。

记忆检索先采用标签、角色和事件关联，设置严格条数及长度预算。是否需要向量检索，等真实回忆规模与召回问题出现后再决定。

删除或关闭引用只保证停止本插件后续注入，不保证删除已经进入宿主历史或模型上下文的文字。界面和指南要准确解释这一点。

新回忆与宿主通用记忆的职责分别是“插件产生的共同经历”和“日常聊天历史”，不承诺完整替代宿主记忆。

## 8. 如何验证是否值得继续

先以少量内容做 7 至 14 天个人试玩，再邀请少量目标用户验证。该时长为建议，不是统计效力计算。

关键观察：

| 问题 | 检查方法 |
| --- | --- |
| 用户是否主动想再开展活动 | 询问原因，观察不靠额外奖励的再次使用 |
| 角色是否会记得实际发生的内容 | 跨重启、切角色、换话题后的回访案例 |
| 回忆是否准确 | 核对来源、用户更正与错误归属案例 |
| 选择是否有区别 | 对照不同分支的内容、结果与后续回应 |
| 恋人阶段是否有持续价值 | 单独试玩恋人片段，不只测试从陌生到告白 |
| 会不会打扰或增加压力 | 测试拒绝、取消、延后、未回复与长时间不使用 |
| 模型能力不足时是否仍可用 | 未绑定判断模型、宿主离线、工具未调用、发送无确认 |

工程回归至少包括原子保存、重复提交、跨角色隔离、模式切换、重启恢复、关系重开后的过期结果，以及现有经济与评分不受额外剧情污染。

当前 683 项 Python 测试通过只说明既有基线；本文尚未新增或运行上述功能验证。

## 9. 建议的开发切分

| 阶段 | 可交付结果 | 进入下一步的依据 |
| --- | --- | --- |
| 原型 | 聊天约定验证连续性；可再用一次共同写便签验证参与乐趣 | 确认比普通聊天更有连续性或玩法价值，现有宿主通道能够承载 |
| 第一小版本 | 少量短片段、恋人内容、回忆管理与回访 | 玩家理解发生了什么，能拒绝和纠正，不串角色 |
| 第二小版本 | 角色偏好、礼物故事、共同计划与可选陪伴 | 体验存在自然再次使用价值，内容差异清晰 |
| 后续扩展 | 校验过的事件包与经历纪念物 | 内置内容已验证格式，维护与本地化成本可控 |

不提前承诺版本号或具体工期。真正实施前应先选定原型活动、回忆保存范围和共享规则，再形成对应功能设计。
