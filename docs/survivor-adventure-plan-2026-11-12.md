# 双人幸存者冒险：需求确认、研究与首章规划

日期：2026-11-12。基于插件 0.7.5 与当前本地宿主源码的只读核对。

状态：设计草案。用户明确的方向列为需求；本文补充的机制、数值、技术选择均为推荐，不冒充已经验收的实现。此次只新增文档，不修改宿主、运行中插件或真实存档。

## 1. 已确认的方向

| 项目 | 用户要求 |
| --- | --- |
| 类型 | 参考《吸血鬼幸存者》《Nova Drift》的实时动作肉鸽，而非此前建议的回合制节点地图 |
| 同行 | 玩家与桌宠代表的游戏角色一起冒险；不让真实桌面模型参与操作 |
| 控制 | 玩家控制移动，同行角色自动跟随、辅助战斗 |
| 构筑 | 玩家和同行角色分别选择流派；局内升级强化技能与数值 |
| 世界 | 剑与魔法的原创世界，参考用户喜欢的《无职转生》的世界观感受，名称无需相同 |
| 时长 | 一局约 20 分钟 |
| 局外 | 冒险获得专用金币，局后购买基础属性，下局以强化后的基础属性开局 |
| 解锁 | 可解锁流派、辅助技能；细节由本方案评估 |
| 经济隔离 | 冒险经济不与插件现有礼物金币兑换 |
| 失败与续玩 | 可保存后稍后继续；失败按进度结算 |
| 好感 | 用户倾向于让好感阶段影响战力，具体幅度需要限制和验证 |
| 模型 | 战斗和奖励由规则决定，模型只轻度参与，例如提醒或交流 |
| 插件回馈 | 纪念物、互动内容、待确认经历草稿；沿用玩家确认后留存 |
| 首版 | 一个完整章节，覆盖开局、战斗、失败、通关、商店、存档、归来交流，使用原创轻量美术 |

原有边界继续有效：不修改宿主，不依赖身体点击识别或尚未开放的动作接口，不将提交成功描述为生成、消费或播放完成。

## 2. 研究依据与适用边界

### 2.1 游戏参照

1. **Vampire Survivors，开发者发布的 Steam 商店说明。**明确描述每局收集金币、购买升级、帮助下次挑战，并建议免费退还强化以尝试不同路径。[S1]
   - 采用：局内成长、局外金币强化、低惩罚试配。
   - 不照搬：已有武器、人物、素材及其具体数值；本项目的双人分工需要单独设计。
2. **Nova Drift 官方网站。**强调模块协同、不同构筑和可选挑战模式。[S2]
   - 采用：升级改变行为、技能之间形成协同，重复游玩可以试新组合。
   - 不照搬：飞船惯性控制和大型升级池；它们不是本项目的已确认需求。
3. **Nova Drift 开发者的 Wild Metamorphosis 设计与发布说明。**介绍可选随机升级如何鼓励临场调整，以及重选机会的取舍。[S3][S4]
   - 采用：基础模式支持有方向的构筑，挑战模式再增加不确定性。
   - 不将“随机越多越好”作为结论；随机应创造选择，不能反复提供无法使用的选项。

### 2.2 研究参照

Ryan、Rigby、Przybylski（2006）通过四项研究讨论游戏中的自主、胜任和关系需要与游玩体验、后续游玩意愿的联系。[S5]

由此提出本项目的设计假设：路线与构筑的决定体现自主；可读的敌人预警和可理解的失败体现胜任；同行协同与归来交流体现关系连接。这是设计推论，不是论文验证了我们的玩法。

Tyack、Mekler（2024）的研究检查了 259 项相关 HCI 游戏研究，并批评对自我决定理论的浅层、未经充分论证的运用。[S6]

因此，论文不能证明“20 分钟最合适”“好感加成 8% 最好”或“某种金币曲线一定耐玩”。本文所有具体数值都要通过原型、性能测量和玩家试玩验证。

## 3. 客观审核结论

方向适合做成插件内一个独立的冒险入口，但开发规模已接近一款小型 2D 动作游戏，不能只按新增一页表单估算。

最值得保留的是双人构筑、局外基础成长和冒险后回到相处；最需要控制的是以下问题：

| 风险 | 推荐约束 |
| --- | --- |
| 同行角色只是装饰 | 有可辨认的支援技能、配合效果与战后贡献摘要 |
| 玩家被迫照顾自动队友 | 首版同行不设置独立的死亡条件，不把它做成护送任务 |
| 永久强化掩盖玩法不足 | 属性有上限，提供免费重配，后期目标以新构筑与挑战为主 |
| 高好感成为通关门槛 | 好感只轻度强化同行；零加成也必须可通关 |
| 模型提醒延迟或打断 | 关键提醒由本地规则即时显示；模型不进入战斗时序 |
| 一局内容被反复刷空 | 敌人组合、升级取舍、双人搭配和可选挑战共同提供变化 |
| 频繁保存影响聊天和帧率 | 战斗在前端运行，后台只承担低频检查点与交易 |
| 宿主或浏览器重开导致丢进度 | 明确手动存档与自动检查点的恢复粒度，原型验证后再承诺 |

## 4. 首章玩法方案

### 4.1 世界与表现

暂名“边境林地”，名称可后改。采用俯视 2D 场景：玩家与同行者接受一份边境冒险委托，进入受到魔力异常影响的林地，击败最后的守关敌人后归来。

借鉴用户偏好的方向：魔法需要学习、剑术与法术并存、职业流派有成长路径、两人共同旅行。首章不建立完整大陆、学校、种族谱系或长篇主线。

人物、地名、职业名、魔法规则和图像独立设计。不直接复刻某部作品的专有体系，也不把现有插件立绘当作已经适配好的战斗素材。

桌宠身份通过名字、同行记录和可选头像连接；战场先使用统一的原创小型角色形象。自动还原任意桌宠的外貌不属于首版能力。

### 4.2 操作与失败条件

- 玩家用 WASD 或方向键移动，主攻击自动进行；首版不强制手动瞄准。
- 同行者自动跟随，选择附近目标、辅助玩家；距离过远时归位，不能长时间卡在场外。
- 双方不互相阻挡，不抢经验，不要求玩家追着队友拾取资源。
- 玩家拥有生命值；同行者首版不拥有独立死亡条件，其支援依照冷却工作。
- 玩家生命耗尽时本局结束，依实际完成进度结算，不扣好感。
- 支援治疗与护盾有冷却、强度和恢复上限，不能形成无限无敌。
- 升级、暂停、失焦、窗口隐藏时停止模拟计时；浏览器恢复时不补算后台经过的战斗时间。
- 暂停页提供保存并退出、返回游戏、明确结束并结算。普通刷新或意外关闭不自动判定失败。

不在第一版同时引入冲刺、手动技能、手动瞄准、队友指令和复杂地形寻路；操作强度先由走位与构筑承担。

### 4.3 20 分钟节奏

以下按实际模拟时间计算，阅读升级、暂停和保存时间不计入。

| 时间 | 战斗目标 |
| --- | --- |
| 0—3 分钟 | 少量清楚可辨的敌人，形成最初几次升级，展示同行技能 |
| 3—6 分钟 | 首次精英与职业分支，6 分钟出现小首领 |
| 6—12 分钟 | 敌人组合变化，逐步形成协同，12 分钟出现第二个小首领 |
| 12—18 分钟 | 构筑成型，加入可选高风险目标，避免只靠提高敌人生命拖时长 |
| 18—20 分钟 | 最终首领；击败即通关，20 分钟仍未完成则按未通关结算 |

这是约 20 分钟上限的候选节奏。首领期限是否过紧、前段升级是否过密，均由原型试玩调整。首版不接无尽模式。

## 5. 双人构筑

### 5.1 三种流派原型

| 流派暂名 | 玩家侧行为 | 同行侧行为 | 配合方向 |
| --- | --- | --- | --- |
| 剑卫 | 近身扇形斩击，兼顾生存 | 周期性护盾与近身解围 | 为远程或脆弱构筑创造空间 |
| 元素使 | 弹体与范围法术，可走不同元素分支 | 控制、易伤或低频范围支援 | 聚敌、控制与范围攻击配合 |
| 游侠 | 远程射击，可走贯穿或多重分支 | 标记重点敌人并补充追击 | 集中处理精英与首领 |

玩家和同行分别选择，同流派组合也可用。首版建议两种流派可立即选择，第三种通过可见的冒险目标获得购买资格；初始组合必须覆盖近远程差异。

这个选择只代表本次游戏职业，不改写桌宠本人的性格、宿主身份或设定。

### 5.2 经验与升级

- 共用经验条、共用拾取；不经营两条独立等级进度。
- 升级暂停并提供三个选项，明确标注强化玩家、同行还是双方。
- 在可用候选充足时，保证有当前构筑可用的升级；同行升级不能长期只靠纯随机碰到。
- 首版核心内容预算：6 项通用升级、三种流派各 4 项分支升级、6 项双人协同，共约 24 项定义；等级重复与数值变体不另算新内容。
- 升级不仅提供攻击数值，也改变贯穿、范围、控制、标记、护盾触发等行为。
- 玩家与同行各限制主动技能槽，避免所有流派最后堆成同一套技能。
- 分支可以互斥，选择时展示代价和后续方向；不要求玩家先查攻略才知道组合条件。
- 初始重选次数有限，局外可增加到上限；不允许反复免费刷新直到出现固定最优答案。

候选协同示例：同行控制敌人后玩家范围攻击得到增强；同行护盾被击破时触发玩家的解围技能；玩家命中被标记的精英时加速同行的下一次辅助。具体触发频率和伤害先不定。

## 6. 三层成长与经济

### 6.1 资源分工

| 层级 | 资源与内容 | 局末处理 |
| --- | --- | --- |
| 局内 | 经验、当局技能等级、临时强化 | 结束清空；续玩时恢复 |
| 冒险局外 | 专用冒险金币、已购买基础强化、已解锁流派与辅助 | 保存并用于下局 |
| 插件相处 | 纪念物、归来话题、待确认经历 | 按参与角色保留，玩家选择正式留存 |

首版不再为局内商店新增第二种金币，也不引入抽卡券、体力或每日刷取限制。体验成型后确有用途再增加资源。

冒险金币既可由局内完成目标积累候选收入，也可包含最终通关奖励；实际余额只在后台接受本局结算后增加。经验不兑换永久币，避免升级本身形成无限产币循环。

已有礼物金币、礼物库存、每日聊天资格和送礼额度保持现有规则；两种金币必须在名称、图标和余额位置上清楚区分。

### 6.2 局外商店

| 类别 | 推荐内容 | 限制 |
| --- | --- | --- |
| 基础强化 | 生命、攻击、移动、拾取、开局重选次数 | 有等级上限，可在局外免费退还并重配 |
| 流派解锁 | 第三流派、已有流派的起始变体 | 以新选择为主，不逐个替代旧职业 |
| 支援解锁 | 同行的另一种辅助模式 | 配装有槽位上限，不把所有技能无条件叠加 |

基础强化作用于出征小队；界面逐项写明适用玩家、同行或双方。不让每位宿主角色都从头购买同一份基础属性。

候选上限：生命 +20%、攻击 +10%、移动 +6%、拾取范围 +30%、开局重选次数 +2。它们是分别的初始测试值，不代表总战力只提升某个固定百分比。实际乘算、回血与控制的收益必须一起评估。

攻击速度、冷却缩减和无限成长首版不进入永久商店，先避免过多乘算因素。退还只影响之后的新局，不能改写进行中的快照。

### 6.3 失败与通关结算样例

候选公式：

`冒险金币 = 完成的整分钟 × 6 + 精英奖励 + 两个小首领奖励 + 最终通关奖励`

候选配置：3、9、15 分钟各一个精英，击败各得 10；6、12 分钟的小首领各得 30；最终通关额外 80。暂停、切后台和读取存档不增加时间奖励；每个奖励目标有唯一身份。

| 情况 | 按样例完成目标 | 候选金币 |
| --- | --- | --- |
| 5 分钟失败 | 生存 5 分钟，击败首个精英 | 40 |
| 10 分钟失败 | 生存 10 分钟，击败两个精英及首个小首领 | 110 |
| 20 分钟通关 | 完成全部上述目标 | 290 |

这些是公式演算，不是测得的玩家平均收益，也不是已确定数值。未击败目标不发对应奖励，满 20 分钟未击败最终首领不发通关奖励。

基础强化前几级候选价格从 40、80、120、180、260 递增，使一次有实际进展的失败也可能完成早期购买。流派和辅助解锁设可见条件并使用同一种冒险金币；不另外要求稀有代币。

需比较每分钟收益，确认“开局马上送死重来”不会优于正常挑战。可通过目标奖励和非前置集中收入调整，不使用扣除全部失败收益的惩罚补救。

## 7. 好感影响战力的处理

保留用户的方向，但将好感定义为同行的轻度默契加成：

| 当前有效阶段 | 同行输出/支援强度候选加成 |
| --- | --- |
| 陌生 | +0% |
| 熟悉 | +2% |
| 好感 | +4% |
| 暧昧 | +6% |
| 恋人 | +8% |

仅对选定的一项综合支援强度系数生效，不同时叠加输出、冷却、控制时长和治疗，控制不因好感突破上限。不能用这张表直接推算整队战力；需测试它与不同流派的实际收益。

- 在开局由后台读取当前生效关系，保存阶段、来源 scope 和加成快照。本局不因聊天、切角色或关系模式变化而重新计算。
- 共用好感模式使用现有共用关系，不虚构各角色的独立好感；冒险经历仍属于实际同行角色。
- 保留“已确认恋爱”与“当前亲近阶段”的区别，战力读取当前有效阶段，文案表达依据实际关系事实。
- 提供关闭默契战力加成的选项，关闭后仍保留关系相关文案。
- 零好感、零永久强化也要能以技巧和正常构筑完成普通难度。是否达成需要真人试玩，不能只看模拟胜率。
- 游戏胜负不直接加减好感，不自动告白，不解锁现有关系尚未允许的亲密互动。
- 不自动永久保存开局时的好感优势；结束本局后，下局重新读取。

暂不做排行榜；未来加入时需区分永久强化、默契加成与挑战规则，不能混合比较。

## 8. 模型、提醒与共同经历

### 8.1 战斗内

低血量、首领出现、重要支援触发先使用本地规则和经过审校的模板。低血量提醒按阈值穿越触发，并有恢复阈值和冷却，避免每帧或每次受伤重复提醒。

首版不依赖真实模型在战斗中即时返回文字，更不调用宿主语音来承担关键警报。可以预留出征前生成少量非关键台词的接口，但模型失败、迟到或未配置时，模板完整可用。真正实时生成的必要性留给原型体验决定。

战斗期间的提醒显示在游戏内，不反复向宿主普通聊天插入消息；首版模型参与集中在玩家主动点击的归来交流。

### 8.2 结束后

1. 先保存真实结果和金币结算；模型故障不影响资产与继续游玩。
2. 展示结果、双方流派、实际击败目标、关键协同与下一目标。
3. 首次完成的目标可以发一次纪念物；重复通关不能重复领取同一首次奖励。
4. 玩家可点击“聊聊这次冒险”，通过现有宿主通道提交简短的结构化事实与邀请。
5. 将其明确表述为“一起游玩的剑与魔法冒险”，不让模型把虚构战斗当作现实经历。
6. 可预览并编辑一份经历草稿。共同经历关闭时不偷偷开启或写入；玩家明确开启后才执行既有流程。
7. 正式记录仍受现有每角色 30 条等容量约束；满额时允许只看结算，不删除旧回忆。

结果已保存、邀请已提交、观察到相关回应、草稿已创建、玩家已正式留存是不同状态，不合并成一个“完成”标志。重试回应不重发金币或重复创建草稿。

## 9. 重复游玩的目标

| 阶段 | 玩家目标 | 系统提供什么 |
| --- | --- | --- |
| 前几局 | 理解走位、升级与同行，走得更远 | 失败收入、早期基础强化、明确的下一目标 |
| 首次通关 | 打完整章 | 一次性纪念物、首通后日谈入口、可选挑战资格 |
| 通关之后 | 试另一组双人搭配或分支 | 组合记录、另一流派与支援模式、不同事件结果 |
| 熟练之后 | 在自选约束下完成挑战 | 更快敌人、精英变化或治疗限制中的少量可选规则 |
| 首章探索完 | 自由重玩或等待下一章 | 清楚显示已完成内容，不以无限涨价拖延 |

首版建议最多三个挑战修饰，不一开始排列几十个难度等级。挑战主要奖励独特纪念、记录和有限额外冒险币；不把基础玩法或恋爱进展锁在高难挑战之后。

局内随机重点放在升级选项、敌人组合与可选事件目标。地图先保持清晰的一个场地主题，不以程序随机地形替代战斗设计。

首章不做每日签到、限时活动、体力和错过即失去的奖励；玩家可以连续玩，也可以暂停数天后回来。

## 10. 承载方式与代码边界

### 10.1 已核实的源码事实

- 当前插件 `plugin.toml` 使用 `ui/panel.tsx` 承载原有关系面板。
- 宿主 `frontend/plugin-manager/src/components/plugin/hosted/hostedTsxModule.mjs` 的 `assertHostedImportContract` 只允许相对模块与 UI kit 等规定导入，不能在当前 Hosted TSX 中直接裸导入 Phaser。
- 宿主 `plugin/neko_plugin_cli/commands/validate_cmd.py` 和 `plugin/core/ui_manifest.py` 支持 static 面板声明。
- `plugin/sdk/plugin/base.py` 有 `register_static_ui()`。
- `frontend/plugin-manager/src/components/plugin/HostedSurfaceFrame.vue` 中静态面板和 Hosted TSX 的沙箱、通信处理有区别；不能假定同一桥接代码可直接通用。
- `frontend/plugin-manager/src/views/PluginDetail.vue` 有面板专注显示与 iframe 键盘边界相关代码。

这些证明当前源码存在候选能力，不代表运行中的宿主构建已通过游戏承载测试。此次没有安装游戏或运行冒险原型。

### 10.2 推荐方案

优先验证独立静态游戏面板，在插件内打包游戏引擎与素材，通过宿主已支持的方式打开；原有关系页保留其职责。前端引擎候选为 Phaser，其官方文档列出浏览器 2D、WebGL/Canvas、JavaScript/TypeScript 支持。[S7]

使用现成引擎承担渲染、场景和基础碰撞等能力，自行编写本项目的技能、协同、敌人与经济规则。引擎在构建期锁版本并随包发布，不在玩家运行时依赖公共 CDN。

不能为了嵌入引擎修改宿主，不能通过规避 Hosted TSX 导入限制实现。若静态面板无法通过现有接口完成必要通信，先报告具体限制并调整承载方式，不先承诺完整玩法。

### 10.3 推荐职责

| 边界 | 职责 |
| --- | --- |
| 游戏前端场景与规则 | 移动、敌人、碰撞、技能、波次、局内随机状态、暂停 |
| 冒险规则域 | 流派目录、购买规则、完成条件、奖励计算、版本与快照校验 |
| 冒险运行时服务 | 活跃局身份、并发修订、检查点、原子保存、结算与回执 |
| 插件 SDK 入口 | 认证后的调用入口、启停代次、锁和服务组合 |
| 归来连接 | 从已保存结果创建邀请或待确认经历，不反向决定游戏奖励 |

新增文件名待技术原型后确定，不先在 `__init__.py` 或 `panel.tsx` 内堆入完整战斗系统。

## 11. 存档、结算与性能约束

### 11.1 权威状态与恢复

- 首版全局只允许一局活跃冒险，开局绑定同行身份与规则版本；多个窗口只能有一个有效控制会话。
- 关系快照、流派、已购买基础属性、随机状态、模拟 tick、生命、等级、冷却、敌人和目标状态进入检查点。
- 随机状态随局保存，读档不重新刷新升级候选或奖励；保存正在打开的升级选择。
- 手动“保存并退出”必须等后台确认保存后才显示可退出；失败保留当前局并允许重试。
- 自动检查点候选间隔为 10 秒，并在关键升级、目标完成后触发；频率与载荷待测。意外崩溃最多恢复到已确认的检查点，不能保证最后一帧。
- 异步检查点按修订排序，旧请求不能覆盖新存档；读档和结算也核验当前控制会话。
- 暂停/禁用插件后旧会话不得继续写入；恢复时显式重新取得控制，不能边运行边默认重连。
- 升级不能直接丢弃未结算旧局；按版本迁移或保留旧文件并提示处理，不静默重开。

推荐把游戏检查点与冒险钱包存入独立版本文件，如 `adventure.json`，一次结算在同一文件事务内完成“终止本局、收入、首次奖励、回执”。这是候选结构，需先验证现有存储边界。

共同经历仍在现有关系存档中，通过玩家点击后的独立、可重试请求创建草稿，不假定两个文件能一次原子提交。

### 11.2 幂等与校验

- 前端不能直接提交“给我多少金币”；提交游戏进度，后台按当前局身份、规则和合理上限计算。
- 同一局只能从进行中进入一次终态，失败结算与通关结算互斥。
- 结算响应丢失后查询或重放同一请求，不再次增加资产。
- 不仅依赖会被淘汰的最近几十条交易回执；需要持久终态/结算序号等防重依据，旧局不能在回执过期后重新结算。
- 局外购买采用修订与请求身份，余额、强化和回执一起保存；进行中的开局属性不受购买影响。
- 当前定位是本地单人游戏，前端快照的校验不等于可防本机用户篡改。首版不宣称具备竞技防作弊能力，也不为此先做服务端全帧模拟。

### 11.3 性能

- 战斗帧不逐帧调用 Python、不逐帧写盘、不为每个敌人创建 UI 组件。
- 场景运行在游戏引擎中，关系面板不以战斗频率刷新。
- 空间查询、对象复用、弹体寿命、经验拾取合并与特效预算需要结合引擎实测。
- 设定敌人、弹体和特效的明确预算，不能为了宣传“千怪同屏”无界增加对象。
- 首个性能目标是在用户机器上与宿主同时运行时争取稳定 60 FPS；不达标时缩减特效、提供 30 FPS 模式或降低对象预算，不改变游戏时间来补偿卡顿。
- 记录帧耗时分布、对象峰值、检查点大小、保存延迟以及宿主并行负载；未测量前不承诺性能。

## 12. 分步实施与验收

| 阶段 | 交付 | 通过条件 |
| --- | --- | --- |
| A：承载验证 | 静态游戏页、引擎加载、移动与自动跟随、插件读写最小样例 | 不改宿主；素材可加载；通信可用；失焦暂停；重开能读回测试状态 |
| B：战斗原型 | 一个场地、基础敌人、自动攻击、两个初始流派、升级选择 | 能辨认双方贡献；走位有意义；自动队友不会拖累玩家；最坏负载测量可接受 |
| C：完整首章 | 约 20 分钟波次、首领、第三流派、基础商店与金币结算 | 失败、主动结束、通关都正确结算；重开、丢响应、并发窗口不重复发放 |
| D：相处连接 | 纪念物、归来邀请、经历草稿、有限好感加成 | 不虚构现实经历；不会自动开启共同经历；模型故障不影响游戏 |
| E：首版验收 | 原创素材、音量与提醒设置、窄窗口状态、旧存档兼容、导入包 | 完整游玩及恢复回归通过，原有关系与商店测试继续通过 |

第一步不是直接写全部内容，而是完成 A 的技术验证。A 只能证明能承载，B 才验证是否值得扩成完整首章；这两步仍属于同一完整章节的开发路径。

具体测试至少覆盖：零关系加成与最高加成、不同流派配对、流派升级相互作用、挂机收益、暂停时间、失败收益、断线后结算、保存失败回滚、旧调用拒绝、控制窗口互斥、规则升级兼容、经历容量满额、模型迟到及结果未知。

## 13. 尚需真人验证的判断

- 自动攻击是否足够有操作感，是否确实需要冲刺或一个主动按钮。
- 20 分钟是否适合用户的桌面使用习惯；不能从竞品时长直接下结论。
- 同行的支援是否清楚、有用，是否出现等待治疗或绕圈拖时长的最优玩法。
- 免费重配与永久强化是否让失败有进展，同时保留零强化通关可能。
- 好感加成是否让不同角色选择失衡，是否产生被迫刷关系的感受。
- 通关后是否想主动换搭配再玩，还是只为了金币重复劳动。

这些问题先通过原型、结构化试玩记录和用户反馈回答，不使用论文或简单模拟替代实玩。日志默认不保存聊天正文，也不自动上传遥测。
